# ⚖️ تحليل المفاضلات الهندسية (Trade-offs Analysis)

في هندسة البرمجيات للأنظمة الموزعة والـ Enterprise POS، لا توجد "حلول مثالية"، بل توجد **مفاضلات واعية (Trade-offs)**. توثق هذه الصفحة الخيارات التي تم دراستها وأسباب تفضيل حل على آخر في خدمة `SuperMarket.Identity`:

---

## 1. مزود الهوية: Keycloak مقابل Auth0 مقابل Custom ASP.NET Identity

| وجه المقارنة | Keycloak (الخيار المعتمد) | Auth0 / Okta (SaaS) | Custom Identity (بناء يدوي من الصفر) |
|---|---|---|---|
| **التكلفة والترخيص** | **مجاني بالكامل (Open Source)** بدون قيود على عدد الكاشيرية والفروع. | مكلف جداً مع التوسع وزيادة المستخدمين (Pay-per-MAU). | مجاني برمجياً، لكن مكلف جداً في الصيانة والتطوير. |
| **البيئة المحلية والشبكة الداخلية** | يعمل بالكامل محلياً داخل **Docker** وعلى شبكات الفروع الداخلية. | يتطلب اتصالاً سحابياً دائماً بالإنترنت لكل عملية. | يعمل محلياً. |
| **المسؤولية الأمنية** | **مفوضة لمعيار عالمي (OIDC)** ومجتمع أمني ضخم. | مفوضة بالكامل للشركة السحابية. | **مسؤولية الفريق بنسبة 100%** (خطر ثغرات مرتفع). |
| **الجهد التشغيلي** | يحتاج لإدارة الحاوية والـ Database التابعة لها. | صفر جهد تشغيلي (Managed Service). | يحتاج لصيانة كود التشفير والـ Refresh Tokens يدوياً. |
| **الخلاصة المعمارية** | **الخيار الأفضل:** يمنح استقلالية تامة، أماناً معتمداً، وتكلفة صفرية مع أعلى معايير الـ Enterprise. | مناسب للتطبيقات السحابية البحتة دون قيود شبكة محلية. | **غير منصوح به نهائياً** في أنظمة التجزئة الحساسة. |

## 2. تسجيل دخول الكاشير: Fast PIN Login مقابل Hosted Keycloak Browser UI

| وجه المقارنة | Fast POS PIN Login (الخيار المعتمد لنقاط البيع) | Keycloak Hosted Web UI (OAuth 2.0 PKCE) |
|---|---|---|
| **تجربة الكاشير في السوبرماركت** | **سرعة استثنائية (< 1 ثانية):** الكاشير يدخل رمزه السري ويبدأ مسح الأصناف فوراً. | بطيء وغير عملي: يتطلب فتح متصفح ويب وإدخال بريد وكلمة مرور طويلة أمام الزبائن. |
| **التبديل بين الورديات (Switching)** | تبديل فوري بين موظفي الكاشير بنقرة زر على شاشة اللمس. | تسجيل خروج من المتصفح وإعادة توجيه كاملة تأخذ وقتاً طويلاً. |
| **الموافقة الاستثنائية للمشرف (Override)** | إدخال رمز المشرف في نافذة منبثقة سريعة دون مقاطعة جلسة الكاشير. | مستحيل دون تسجيل خروج الكاشير بالكامل ودخول المشرف بحسابه. |
| **الاستخدام المعتمد** | **معتمد ومخصص لشاشات نقاط البيع (POS Terminals).** | **معتمد للوحات تحكم الإدارة (Admin Web Portal).** |

## 3. التحقق من الـ Token: Stateless JWT via JWKS مقابل Stateful Introspection

| وجه المقارنة | Stateless JWT via JWKS (الخيار المعتمد) | Stateful Token Introspection |
|---|---|---|
| **الأداء والـ Latency** | **فائق السرعة (< 1ms)**؛ فحص محلي في الذاكرة دون طلبات شبكة. | بطيء (50-100ms)؛ اتصال شبكي مع كل مسح صنف أو عملية دفع. |
| **استقرار الكاشير وطابور الزبائن** | استمرار الكاشير في البيع حتى لو كان سيرفر Keycloak تحت ضغط. | انهيار نقاط البيع وتحول Keycloak إلى **Single Point of Failure**. |
| **إلغاء الجلسات الفوري (Revocation)** | يتطلب انتهاء صلاحية الـ Access Token (15 دقيقة) أو إبطال الكاش عبر الـ Events. | إلغاء فوري للجلسة لحظياً من قاعدة بيانات Keycloak. |
| **الخلاصة المعمارية** | **الخيار الأساسي لأنظمة نقاط البيع:** نعتمد توكن قصير الأجل مع إبطال عبر الأحداث لجمع السرعة مع الأمان. | يسبب بطء طوابير السوبرماركت ولا يناسب الـ High Throughput. |

## 4. نموذج عزل الفروع: قاعدة بيانات موحدة بعزل منطقي مقابل DB مستقلة لكل فرع

| وجه المقارنة | Shared Central Multi-Branch DB (الخيار المعتمد) | Database per Branch (قاعدة بيانات محلية في كل متجر) |
|---|---|---|
| **التقارير المجمعة للإدارة** | **سهل وفوري:** لوحة تحكم الإدارة تستعرض مبيعات كافة الفروع لحظياً. | يتطلب حلول مزامنة بيانات معقدة جداً (CDC / ETL Sync). |
| **نقل الموظفين والصلاحيات** | فوري وبسيط: تعديل فرع الكاشير ينعكس على الفور في كافة الفروع. | يتطلب مزامنة حساب الكاشير عبر عدة خوادم مستقلة. |
| **التعقيد التشغيلي** | إدارة وصيانة خادم PostgreSQL مركزي واحد عالي التوفر (HA). | صيانة مئات الخوادم وقواعد البيانات في كل فرع جغرافي. |
| **العزل الأمني** | يتم برمجياً عبر الـ Query Filters وفحص `BranchId` في التوكن. | عزل فيزيائي تام. |
| **الخلاصة المعمارية** | **الخيار المثالي للمنصات المركزية الحديثة مع دعم Caching محلي في نقاط البيع.** | مكلف تشغيلياً ويتطلب فريق IT مخصص في كل متجر. |

## 5. تصميم المجال: Pragmatic DDD & Invariants مقابل Anemic CRUD

| وجه المقارنة | Pragmatic DDD & Rich Entities (الخيار المعتمد) | Anemic CRUD (خصائص عامة مفتوحة) |
|---|---|---|
| **حماية قواعد الفروع والكاشير** | **مضمونة 100%:** لا يمكن تشغيل جهاز POS بدون فرع، ولا تفعيل كاشير بدون PIN مشفر. | **معدومة:** أي Controller يمكنه إنشاء سجلات مكسورة أو غير مرتبطة بفرع. |
| **توافق EF Core** | Constructor خاص لـ EF Core + دوال أعمال صريحة (`TransferToBranch`, `RegisterDevice`). | استدعاء Constructor واحد مفتوح يخلط بين تهيئة الكيان وتحميله من الـ DB. |
| **الوضوح ونية الأعمال** | أسماء معبرة تحاكي واقع السوبرماركت. | حقول مفتوحة بدون أي سياق تجاري. |
| **الخلاصة المعمارية** | **الخيار المعتمد لضمان استقرار نظام الـ Enterprise ومنع الأخطاء البشرية البرمجية.** | مناسب فقط للنماذج التجريبية البسيطة. |
