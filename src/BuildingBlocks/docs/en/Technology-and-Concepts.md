# SuperMarket.BuildingBlocks — Technology and Concepts

> **Scope:** Comprehensive audit of programming concepts, enterprise patterns, and framework technologies implemented in `SuperMarket.BuildingBlocks`.

---

## 1. Result Pattern & Explicit Error Modeling

### Status: `Implemented`
* **Where:** `Results/Result.cs`, `Results/ResultT.cs`, `Results/Error.cs`, `Results/ErrorType.cs`
* **What:** Encapsulates the success or failure of an operation in an immutable object (`Result` or `Result<TValue>`) paired with a strongly-typed `Error` description and `ErrorType`.
* **Why:** Eliminates the use of exceptions for expected business failures (e.g. invalid barcode, out of stock, closed register shift). Exceptions in .NET are computationally expensive due to stack trace generation and create invisible control-flow jumps.
* **How:**
  - `Result` has a `protected internal` constructor enforcing state invariants: success cannot have an error, and failure cannot have `Error.None`.
  - Factory methods (`Result.Success()`, `Result.Failure(error)`, `Result.Create(value)`) provide safe instantiation.
  - `Result<TValue>` guards its `Value` property: attempting to read `Value` on a failed result throws an `InvalidOperationException`.
* **Trade-offs:**
  - *Benefits:* Explicit API contracts, 0 stack-trace overhead, compiler-enforced handling, deterministic HTTP status mapping.
  - *Costs:* Requires consumers to inspect `IsSuccess` or chain calls with functional combinators instead of allowing exceptions to bubble up.
* **Related Concepts:** Railway-Oriented Programming, Maybe/Either Monad, Null Object Pattern.

## 2. Railway-Oriented Programming (ROP)

### Status: `Implemented`
* **Where:** `Results/ResultExtensions.cs`
* **What:** Provides functional chaining extensions (`Match`, `Ensure`, `Map`, `Bind`) to compose operations as parallel tracks: a green track for success and a red track for failure.
* **Why:** Simplifies complex business workflows by avoiding deeply nested `if (!result.IsSuccess)` blocks and forcing exhaustive handling of both branches at API boundaries.
* **How:**
  - `Match`: Forces the caller to provide two delegates (`onSuccess` and `onFailure`) returning a unified output type `TOutput`.
  - `Ensure`: Validates a predicate against the inner value; if false, switches to a failure result with the given `Error`.
  - `Map`: Transforms the inner value `TValue` to `TOutput` if successful, preserving any prior error.
  - `Bind`: Chains a subsequent operation returning a `Result<TOutput>`, short-circuiting immediately if the previous step failed.
* **Trade-offs:**
  - *Benefits:* Highly readable linear pipelines, declarative business rules, clean Minimal API / Controller responses.
  - *Costs:* Slight allocation overhead from delegate invocations; steep learning curve for developers unfamiliar with functional paradigms.
* **Related Concepts:** Monadic Binding, Functional Programming in C#, Short-Circuit Evaluation.

## 3. Domain-Driven Design (DDD) Primitives

### Status: `Implemented`
* **Where:** `Domain/Entity.cs`, `Domain/AggregateRoot.cs`, `Domain/ValueObject.cs`, `Domain/DomainEvent.cs`
* **What:** Base building blocks for modeling rich enterprise domain logic.
* **Why:** Provides a consistent framework for entity identity, aggregate consistency boundaries, value object immutability, and domain event lifecycle.
* **How:**
  - `Entity<TId>`: Implements `IEquatable<Entity<TId>>`. Identity equality is determined by `Id` rather than object reference. Transient entities (unassigned default `Id`) are never equal unless sharing reference equality.
  - `AggregateRoot<TId>`: Inherits from `Entity<TId>` and implements `IAggregateRoot`. Holds an internal `List<IDomainEvent>` exposed via a read-only collection. Exposes `AddDomainEvent`, `RemoveDomainEvent`, and `ClearDomainEvents`.
  - `ValueObject`: Enforces structural equality by evaluating an `IEnumerable<object?>` generated by the abstract `GetEqualityComponents()` method.
  - `DomainEvent`: Abstract record implementing `IDomainEvent` with default `Guid EventId` and `DateTimeOffset.UtcNow`.
* **Trade-offs:**
  - *Benefits:* Protects domain invariants, standardizes aggregate boundaries, encapsulates event publishing logic.
  - *Costs:* Requires developers to override `GetEqualityComponents()` on value objects and explicitly identify Aggregate Roots vs internal Entities.
* **Related Concepts:** Domain-Driven Design, Structural Equality, Event-Driven Architecture.

## 4. Capability Interfaces (Composition over Inheritance)

### Status: `Implemented`
* **Where:** `Domain/IAuditableEntity.cs`, `Domain/ISoftDeletable.cs`, `Domain/IActivatable.cs`, `Domain/IAggregateRoot.cs`
* **What:** Granular marker and property interfaces applied to domain entities to grant specific behaviors.
* **Why:** Avoids the "God Entity" anti-pattern where a single monolithic `BaseEntity` forces unwanted fields (such as `DeletedAt` on an immutable audit log or `IsActive` on an order line) onto all tables.
* **How:**
  - Entities compose only the capabilities they require:
    ```csharp
    public class CashierShift : AggregateRoot<Guid>, IAuditableEntity, ISoftDeletable, IActivatable
    ```
  - Interceptors (`AuditSaveChangesInterceptor`) and ModelBuilder extensions inspect entries via reflection / type checking and apply automation uniformly.
* **Trade-offs:**
  - *Benefits:* Clean database schemas, high cohesion, interface segregation (ISP), reusable persistence policies.
  - *Costs:* Entities implement multiple interfaces; properties must be defined individually in entity classes or interfaces.
* **Related Concepts:** Interface Segregation Principle (ISP), Composition over Inheritance.

## 5. MediatR Pipeline Behaviors (Decorator Pattern)

### Status: `Implemented`
* **Where:** `Application/ValidationPipelineBehavior.cs`, `Application/LoggingPipelineBehavior.cs`, `Application/PerformancePipelineBehavior.cs`
* **What:** Middleware pipeline for CQRS requests implementing `IPipelineBehavior<TRequest, TResponse>`.
* **Why:** Separates cross-cutting infrastructure concerns (validation, logging, metrics) from business use case handlers.
* **How:**
  - **Validation Behavior:** Collects all registered `IValidator<TRequest>`, invokes `ValidateAsync` concurrently using `Task.WhenAll`, aggregates error messages, and creates a failure `Result` via reflection (`CreateValidationResult`) if errors exist.
  - **Logging Behavior:** Logs request entry, intercepts `Result.IsFailure` to log warnings with error codes, and catches unhandled exceptions to log errors before re-throwing.
  - **Performance Behavior:** Wraps execution in a `Stopwatch`, publishes native metrics, and logs a warning when execution duration exceeds the configured threshold.
* **Trade-offs:**
  - *Benefits:* Handlers remain 100% focused on business logic; cross-cutting features are guaranteed to execute for every request.
  - *Costs:* Adds slight invocation overhead per behavior; requires MediatR container registration.
* **Related Concepts:** Decorator Pattern, Aspect-Oriented Programming (AOP), CQRS.

## 6. OpenTelemetry Native Metrics (`System.Diagnostics.Metrics`)

### Status: `Implemented`
* **Where:** `Application/PerformancePipelineBehavior.cs`
* **What:** High-performance in-memory metrics instrumentation using the native .NET 8/9/10 `System.Diagnostics.Metrics` API.
* **Why:** Exposes enterprise metrics for Prometheus, Grafana, and OpenTelemetry collectors without introducing heavy third-party SDK dependencies into `BuildingBlocks`.
* **How:**
  - Declares a static `Meter`: `new Meter("SuperMarket.POS.Core", "1.0.0")`.
  - Defines a `Counter<long>` (`pos_requests_total`) tracking request throughput tagged with `request_name`.
  - Defines a `Histogram<double>` (`pos_request_duration_ms`) tracking execution latency distributions.
  - Executed inside a `finally` block to ensure metrics are recorded even when requests throw unhandled exceptions.
* **Trade-offs:**
  - *Benefits:* Zero external package dependencies, allocation-free telemetry, native OpenTelemetry export compatibility.
  - *Costs:* Requires consuming Web API projects to configure OpenTelemetry Exporters (e.g. Prometheus / OTLP exporter) to collect and visualize data.
* **Related Concepts:** OpenTelemetry, Observability, SLA Monitoring, RED Metrics Pattern.

## 7. EF Core SaveChanges Interceptors

### Status: `Implemented`
* **Where:** `Infrastructure/AuditSaveChangesInterceptor.cs`, `Infrastructure/DispatchDomainEventsInterceptor.cs`
* **What:** Custom interceptors extending `SaveChangesInterceptor` to hook into the EF Core persistence lifecycle.
* **Why:** Automates cross-cutting database requirements without polluting domain entities or forcing developers to remember manual calls in every repository or handler.
* **How:**
  - `AuditSaveChangesInterceptor`:
    - Processes `ISoftDeletable` first: intercepts `EntityState.Deleted`, converts to `EntityState.Modified`, and sets `IsDeleted = true`, `DeletedAt`, and `DeletedBy`.
    - Processes `IAuditableEntity`: sets `CreatedAt` / `CreatedBy` on `Added`, and `UpdatedAt` / `UpdatedBy` on `Modified`.
    - Explicitly sets `IsModified = false` on creation metadata during updates to enforce immutability.
    - Utilizes injectable `TimeProvider` (defaulting to `TimeProvider.System`) for deterministic unit testing of timestamps.
  - `DispatchDomainEventsInterceptor`:
    - Queries `ChangeTracker` for entries implementing `IAggregateRoot` with queued events.
    - Clears domain events from aggregates before publishing to prevent infinite recursive loops.
    - Dispatches each `IDomainEvent` via `IPublisher.Publish(...)` in-process.
* **Trade-offs:**
  - *Benefits:* Zero manual audit code in handlers, impossible to forget soft deletes, clean separation of domain event dispatching.
  - *Costs:* In-process event publishing occurs inside the `SavingChanges` pipeline before transaction commit; if an event handler fails, the database transaction rolls back.
* **Related Concepts:** Entity Framework Core Interception, In-Process Domain Event Publishing, TimeProvider.

## 8. Global Query Filters for Soft Deletion

### Status: `Implemented`
* **Where:** `Infrastructure/ModelBuilderExtensions.cs`
* **What:** Automatic EF Core query filter extension applying `e => !e.IsDeleted` across all entities implementing `ISoftDeletable`.
* **Why:** Eliminates the risk of leaking logically deleted records into queries, reports, or cashier displays.
* **How:**
  - Iterates over `modelBuilder.Model.GetEntityTypes()`.
  - Builds an `Expression.Lambda` filtering `IsDeleted == false` for every entity where `typeof(ISoftDeletable).IsAssignableFrom(entityType.ClrType)`.
  - Can be bypassed when needed by calling `.IgnoreQueryFilters()`.
* **Trade-offs:**
  - *Benefits:* Complete protection against data leaks; zero repetitive `where !x.IsDeleted` clauses.
  - *Costs:* Developers must be aware of `.IgnoreQueryFilters()` when writing administrative or restore features; slightly complicates navigation property joins if soft-deleted parents exist.
* **Related Concepts:** Expression Trees, EF Core Global Query Filters, Soft Delete Pattern.

## 9. Dual-Strategy Pagination (Offset vs. Keyset)

### Status: `Implemented`
* **Where:** `Application/PaginationParams.cs`, `Application/PagedList.cs`, `Application/CursorParams.cs`, `Application/CursorPagedList.cs`, `Application/PaginationSettings.cs`
* **What:** Provides two distinct pagination mechanisms tailored to different workload characteristics.
* **Why:** In high-volume POS systems, classic offset pagination (`Skip`/`Take`) causes severe database performance degradation on million-row tables due to table scans and expensive `COUNT(*)` queries.
* **How:**
  - **Offset Pagination (`PagedList<T>`):**
    - Takes `PageNumber` and `PageSize` (clamped defensively between 1 and `MaxPageSize`).
    - Executes `CountAsync` followed by `.Skip(...).Take(...)`.
    - Intended for administrative screens with page jumps and previous/next buttons.
  - **Keyset / Cursor Pagination (`CursorPagedList<T, TCursor>`):**
    - Takes `Cursor` (e.g., timestamp or sequence ID) and `PageSize`.
    - Filters records using an index seek (`WHERE Id > @cursor ORDER BY Id ASC LIMIT @pageSize + 1`).
    - Zero `COUNT(*)` overhead; $O(1)$ constant-time performance regardless of depth; immune to data drift.
    - Intended for high-throughput POS cashier transactions, audit logs, and infinite-scroll feeds.
* **Trade-offs:**
  - *Benefits:* Optimal performance for each use case; built-in defensive bounds against denial-of-service queries.
  - *Costs:* Keyset pagination does not provide total page counts or random page jumps.
* **Related Concepts:** Keyset Pagination, Cursor-based Streaming, Database Index Seeks.

## 10. Centralized RFC 7807 Problem Details

### Status: `Implemented`
* **Where:** `Results/ResultProblemDetailsExtensions.cs`, `Infrastructure/GlobalExceptionHandler.cs`
* **What:** Standardized HTTP API error response generation complying with the IETF RFC 7807 specification.
* **Why:** Establishes a uniform error format across all microservices so mobile, web, and cashier frontend applications can parse errors consistently.
* **How:**
  - `ToProblemDetails()` maps `ErrorType` enum to standard HTTP status codes:
    - `Validation` $\rightarrow$ 400 Bad Request
    - `NotFound` $\rightarrow$ 404 Not Found
    - `Conflict` $\rightarrow$ 409 Conflict
    - `Unauthorized` $\rightarrow$ 401 Unauthorized
    - `Forbidden` $\rightarrow$ 403 Forbidden
  - Appends custom extension properties such as `errorCode` and RFC type URIs.
  - `GlobalExceptionHandler` implements `IExceptionHandler`: catches unexpected 500 errors, logs them with `Activity.Current?.Id` / `TraceId`, and returns a safe sanitized ProblemDetails envelope without leaking sensitive stack traces.
* **Trade-offs:**
  - *Benefits:* Industry-standard error contract, clean frontend integration, secure exception masking.
  - *Costs:* Requires consumers to use `.ToProblemDetails()` when returning error responses from endpoints.
* **Related Concepts:** RFC 7807, IProblemDetailsService, Distributed Tracing.

| Technology / Pattern | Status | Reason & Architectural Location |
| :--- | :--- | :--- |
| **Outbox Pattern / Distributed Messaging** | `Not Implemented` in BuildingBlocks | Cross-service integration events (RabbitMQ/MassTransit) belong in specific service infrastructure or a dedicated messaging library, not within core in-process BuildingBlocks. |

| **Database Migrations** | `Not Implemented` in BuildingBlocks | Migrations belong exclusively to concrete service DbContexts (`SuperMarket.Sales.Infrastructure`, etc.). |
