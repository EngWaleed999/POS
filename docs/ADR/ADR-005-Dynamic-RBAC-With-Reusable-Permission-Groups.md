# 🏛️ سجل القرارات المعمارية (ADR-005)
## معمارية التفويض القائمة على مجموعات الصلاحيات الوسيطة والأدوار الديناميكية (Dynamic RBAC with Reusable Permission Groups)

* **الحالة:** معتمد ومطبق (Accepted & Implemented)
* **التاريخ:** 2026-09-23
* **السياق والمشروع:** `SuperMarket.Identity.Domain` / المنصة المركزية لنقاط البيع (POS)
* **المؤلفون:** Senior Backend Engineer & Architecture Reviewer

---

## 1. Context (سياق المشكلة)

في منظومة نقاط بيع وسوبرماركت مركزي تخدم فروعاً مختلفة الأحجام (من بقالة صغيرة أو فرع محلي إلى هايبر ماركت ضخم متعدد الأقسام):
1. **الصلاحيات الذرية التفصيلية (Fine-Grained Permissions):** صُممت الصلاحيات بنمط `resource:action:scope` (مثل `sales:create:branch`، `inventory:adjust:own`) لضمان تحكم أمني دقيق في كل عملية، مما ينتج أكثر من 80 صلاحية ذرية عبر خدمات النظام.
2. **معضلة الإسناد المباشر (Flat RBAC):** عند ربط الأدوار بالصلاحيات مباشرة بجدول واحد `role_permissions`، يضطر مدير النظام (`SystemAdmin`) إلى فحص واختيار عشرات الصلاحيات الفردية يدوياً عند تعريف كل دور جديد، مما يرفع احتمالية الأخطاء البشرية (Human Configuration Errors) بنسيان صلاحية هامة أو منح صلاحية خطيرة بالخطأ.
3. **معضلة الأدوار الثابتة (Static Enums):** حصر الأدوار في كود ثابت C# `Enum` يجعل إضافة دور سابع أو تعديل مسمى وظيفي مستحيلاً دون تعديل الكود البرمجي وإعادة بناء ونشر التطبيق بالكامل (Deployment Overhead)، وهو ما يتعارض مع متطلبات الأنظمة المؤسسية المرنة.
4. **تكرار الحزم الوظيفية:** الأدوار المتقاربة (مثل كاشير صباحي، كاشير رئيسي، كاشير خدمة ذاتية) تشترك في 90% من الصلاحيات؛ والافتقار لآلية تجميع وسيطة يؤدي لتكرار ربط نفس الصلاحيات يدوياً مراراً وتكراراً.

## 2. Options Considered (الخيارات الهندسية التي تم تقييمها)

### الخيار (أ): الأدوار الثابتة برمجياً (Enum-Based Roles)
* **الوصف:** حصر الأدوار في `Enum` داخل كود C# (`RoleType { Cashier, StoreManager, ... }`).
* **الإيجابيات:** أداء استعلام سريع جداً، سهولة التحقق في الـ Type System.
* **السلبيات والرفض:** غير مرن إطلاقاً؛ لا يمكن لمدير النظام إنشاء دور جديد دون فتح الكود وإعادة النشر؛ غير صالح للتوسع في بيئات السوبرماركت المتعددة.

### الخيار (ب): الربط المباشر بين الدور والصلاحيات (Flat RBAC: `roles` <-> `permissions`)
* **الوصف:** جدول ربط وسيط مباشر `role_permissions` يربط معرّف الدور بمعرّف الصلاحية.
* **الإيجابيات:** هيكل جداول أبسط (3 جداول فقط)، و Join واحد عند استعلام صلاحيات الدور.
* **السلبيات والرفض:** عبء إداري وتكرار لا نهائي في واجهات المستخدم؛ صعوبة تحديث ميزة تشغيلية عبر عدة أدوار؛ زيادة احتمالية منح صلاحيات غير مقصودة.

### الخيار (ج - المعتمد): المعمارية القائمة على حزم العمل الوسيطة والأدوار الديناميكية (Group-Based Reusable RBAC)
* **الوصف:** اعتماد هيكل خماسي الكيانات:
  `Role (1:N) -> RolePermissionGroup (N:1) -> PermissionGroup (1:N) -> PermissionGroupItem (N:1) -> Permission`.
* **الإيجابيات:**
  - تجميع الصلاحيات الذرية في "حزم عمل" قابلة لإعادة الاستخدام (`PermissionGroup`) مثل: "Cashier Basic Operations"، "Inventory Counting Package".
  - الأدوار ديناميكية (`Role Entity`) مع زرع (Seed) 6 أدوار افتراضية لتبسيط البدء السريع للمتاجر الصغيرة.
  - إسناد الحزم المعتمدة للأدوار بضغطة زر واحدة.
* **السلبيات:** زيادة عمق الـ Joins في قاعدة البيانات (معالج بالـ In-Memory / Redis Caching).

## 3. Decision (القرار الهندسي المعتمد)

تم اعتماد **الخيار (ج)** كمعمارية رسمية لإدارة الصلاحيات والتفويض في المنصة، وفق القواعد التصميمية التالية:

### 1. هيكل الكيانات الخمسة:
1. `Permission`: كيان تعريف ذري نقي (Pure Definition Entity)، يحدد `Resource`, `Action`, `Scope`, `Category`. تم تجريده من أي حقول تدقيق أو أوقات زمنية لكونه تصريحاً ثابتاً غير متغير.
2. `PermissionGroup`: كيان يمثل الحزمة التجميعية (`GroupName`, `Description`) دون أي حقول تدقيق.
3. `PermissionGroupItem`: كيان ربط نقي (Pure Join Entity) بمفتاح مركب طبيعي `(GroupId, PermissionId)` بدون مفتاح اصطناعي (Surrogate Key) وبحذف فعلي فقط (Hard Delete).
4. `Role`: كيان الدور الوظيفي الديناميكي؛ يطبق واجهات القدرات `IAuditableEntity` و `IActivatable` عبر **Explicit Interface Implementation** لحماية التغليف، ويعتمد Hard Delete فقط (بشرط عدم وجود مستخدمين مسندين إليه).
5. `RolePermissionGroup`: كيان ربط نقي (Pure Join Entity) بمفتاح مركب طبيعي `(RoleId, GroupId)` بدون مفتاح اصطناعي وبحذف فعلي فقط (Hard Delete).

### 2. مخطط العلاقات البرمجية:

```
Role ──(1:N)──→ RolePermissionGroup ──(N:1)──→ PermissionGroup ──(1:N)──→ PermissionGroupItem ──(N:1)──→ Permission
```

## 4. Consequences & Trade-offs (النتائج والآثار الهندسية)

### الإيجابيات والمكتسبات (Positive Consequences):
* **إعادة الاستخدام العالية (High Reusability):** بناء الحزم الوظيفية لمرة واحدة وإسنادها لمختلف الأدوار القائمة والجديدة.
* **الأمان وتقليل الخطأ البشري (Security Invariant):** اعتماد الحزم ككتل أمنية متكاملة يمنع نسيان صلاحيات حتمية أو تسريب صلاحيات حساسة.
* **أداء الفهارس الفيزيائية (Clustered Index Locality):** استخدام المفاتيح المركبة الطبيعية في جداول الربط يوفر 50% من حجم الفهارس مقارنة بالمعرفات الاصطناعية (`Surrogate Keys`) ويمنع تكرار الربط تلقائياً على مستوى RDBMS.
* **نقاء الدومين (DDD Alignment):** الالتزام الصارم بـ Factory Methods تعيد `Result<T>` وخصائص مغلقة `private set` وحراسات دفاعية صلبة.

### السلبيات وآلية تخفيفها (Negative Consequences & Mitigation):
* **تكلفة الاستعلام المتعدد (Multi-Join Cost):** استرجاع الصلاحيات يتطلب الربط عبر 5 جداول.
* **آلية التخفيف المعتمدة:** لا يتم استعلام قاعدة البيانات في كل طلب؛ بل يتم حساب مصفوفة الصلاحيات لمرة واحدة عند المصادقة وحفظها في الـ Cache (In-Memory / Redis) أو تضمينها في الـ Token، مما يجعل تكلفة التحقق في الـ Middleware أقل من 1ms.

---

## 5. Reconsideration Conditions (شروط إعادة النظر)

يُعاد فتح هذا القرار المعماري وإعادة تقييمه في الحالات التالية فقط:
1. إذا تحول التطبيق إلى نظام مدمج خفيف جداً (Embedded Standalone POS) يعمل على أجهزة محدودة الموارد لا تتطلب أكثر من مستخدمين اثنين وأدوار ثابتة تماماً.
2. إذا تم التحول إلى نموذج تفويض مختلف كلياً مثل Attribute-Based Access Control (ABAC) أو Policy-Based Authorization عبر محرك خارجي مثل OPA (Open Policy Agent).
